# 编写项目实施计划

约定 `<skill_dir>` 为当前技能目录，`<repo_dir>` 为目标仓库根目录。

## 流程

1. 按需读取需求、仓库规范及相关实现、测试、配置和调用方，建立方案所需的事实；按下文原则选择最简实现，处理影响方案的未决问题。
2. 读取 `<skill_dir>/references/plan-document-structure.md`，按其格式写入用户指定路径；未指定时使用 `<repo_dir>/docs/agent_plans/YYYY-MM-DD-<feature-name>.md`。
3. 按可独立交付和验证的边界组织任务，写清修改位置、依赖顺序和完成标准。多个独立子系统可分成多份计划；跨仓或 RPC 任务标明项目、兼容顺序和升级节点。
4. 自审并修复需求遗漏、事实错误、链接失效、前后矛盾和冗余设计，确认计划满足下文输出要求及大小限制。
5. 交付计划路径、关键决策和阻塞项，交由 `execute-project-plan` 执行。本技能只写计划。

## 选择最简实现

- 只设计当前需求必需的内容，不为假设的未来需求增加功能、抽象或配置。
- 优先顺序为：仓库已有实现 → 标准库 → 平台原生能力 → 已安装依赖 → 最小新增实现。核对实际可用性，已有能力满足需求就直接复用；新增依赖或抽象须有具体必要性。
- 一行能清晰完成就不增加包装。方案和任务数量与问题规模相称，同时保留必要的错误处理、兼容措施和验证。

## 决策提问

优先从仓库和文档消除不确定性。只询问证据无法确定、且会改变目标、范围、契约、迁移、验证或交付方式的问题；给出已知事实、选项影响和推荐方案，便于用户直接选择。非阻塞问题记为显式假设并继续。

跨项目所需仓库缺失时，先检查已有 IDL、生成代码、依赖声明或文档能否证明契约。证据不足时请求补充路径或授权获取仓库，或明确缩小规划范围，不凭假设补全跨项目方案。

## 计划语言

- 面向有基本开发知识但不熟悉项目的读者，用自然、具体的中文说明对象、动作、判断标准和预期结果，避免抽象口号、不必要的英文和自造术语。
- 必要的新术语、缩写、概念或陌生的项目专用含义，必须在术语表中通俗解释其含义、用途及必要示例，首次使用时简短解释或链接到条目，全文含义一致。
- 保留准确的代码符号、配置字段、命令、协议名和状态值，以及必要的证据、兼容要求和授权边界。

## 输出契约

- 计划应让零项目上下文的工程师仅凭文件执行。每个任务包含状态、客观完成标志、精确文件与符号、接口或算法约定、按序步骤、验证命令和可观察的预期结果；仅为消除歧义或满足用户要求提供完整代码。
- 验证须证明完成条件并覆盖必要回归及仓库必跑项。用户要求 TDD 或先写测试有助于明确契约时采用失败测试、实现、通过测试的顺序；只在新变更、失败或未解决风险需要时扩大验证。
- 事实须有证据，预期须明确标为预期；不以占位表达掩盖未决问题，写清其影响和解决条件。

## 硬约束

- 每份计划文件最多 256 KiB（262144 字节，按 UTF-8 保存后的实际字节数计算）。超限时按任务或独立交付边界拆分，保留完整步骤、证据和验证要求；具体组织方式见 `references/plan-document-structure.md`。
- 遵循现有架构、代码风格和仓库命令；不要为满足模板编造文件、API、测试或发布步骤。
- 计划可包含提交、推送和 PR 步骤；合并 PR（含启用自动合并）、生产上线或发布阶段推进、回滚或中止发布、生产数据写入或删除、破坏性操作必须明确标注“执行前需用户确认”，写明具体对象、范围、前置验证及回退方式，不得安排为 Agent 自动推进的动作。
- 确认计划或要求“执行计划”“继续”“自动完成”不等于确认敏感操作；已有针对具体操作和范围的用户明确确认可以沿用，范围变化时须重新确认，不能用确认代替验证要求。
- 除计划文件及其目录外不修改代码、配置或运行时状态；除非用户另行要求，不提交或推送计划。
