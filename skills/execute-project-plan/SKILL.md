# 执行项目计划

约定 `<repo_dir>` 为目标仓库根目录，`<plan_path>` 为计划文件路径。

## 执行循环

1. 读取 `<repo_dir>/AGENTS.md`、完整计划（含主计划链接的任务文件）、当前 Git 状态和相关文件，确认计划仍符合仓库事实。没有计划时先使用 `write-project-plan`；不要边猜边实现。恢复执行时核对已勾选步骤、任务状态与已有验证证据；记录与实际不符时先更正，不能仅凭 checkbox 跳过工作。
2. 定位用户指定步骤或首个未完成步骤，说明当前任务、PR 批次、验证及外部依赖，并按下文“技能加载检查”确认所需技能已加载。代码或配置改动缺少批次边界时，按 `write-project-plan` 的“分批交付”补齐。用户已明确要求执行计划时直接推进已授权工作，敏感操作仍按下文单独核对授权；仅提供计划、查询状态或讨论方案不构成实施授权。
3. 按依赖顺序持续推进，每次只处理一个步骤或一组不可分割的原子改动：
   - 进入新任务、切换工作类型或恢复执行时，重新核对所需技能及其加载状态，补齐后再执行相关步骤。
   - 开始任务前把 `**状态：** 未开始` 改为 `进行中`。
   - 在已授权目标内复用仓库既有模式，保留无关改动和 untracked 文件；必要的 import、调用方修复或计划遗漏可纳入当前步骤并更新计划。
   - 若计划与代码冲突或缺少必要步骤，按当前证据修订计划并说明影响；不改变目标、外部契约、风险或授权范围的内部顺序调整可继续。改变上述边界或继续执行不安全时，等待用户确认。
   - 遇到合并 PR、上线等敏感操作，先完成已授权的准备和验证，展示具体对象、操作范围、验证结果、风险及回退方式；尚无用户明确确认时，停止该操作及依赖步骤并请求确认。已确认的范围无需重复询问，范围变化时重新确认。
   - 每完成一个可独立核验的步骤、进入耗时验证或外部等待前，向用户报告当前任务和步骤、已观察到的结果、下一步及阻塞范围；长步骤持续执行时按实际进展更新，不以预计完成时间或主观百分比代替证据。
4. 运行当前步骤适用的计划验证和仓库必跑项。失败时在已授权目标内修复必要文件并重跑受影响检查；通过后不机械重复或扩大验证。需要新授权或无法通过时，在当前任务旁记录阻塞原因、影响的步骤、已取得的证据和恢复条件；暂停依赖该结果的步骤，仍可推进已授权且不依赖该结果的任务，不得将阻塞步骤标为完成。
5. 验证通过后仅局部更新计划：勾选当前 checkbox，并记录“命令、结果、关键证据”；不要粘贴完整日志。任务完成标志达成后写为 `**状态：** 已完成 (YYYY-MM-DD)`。中断或交接前记录当前未完成步骤、已执行动作及结果、待运行的验证和恢复入口，保持未完成步骤未勾选。
   - 每批末尾按已有授权提交并创建或更新该批 PR，核对 diff 范围，记录任务、commit、PR 与验证证据；不把后续独立批次追加进当前 PR。缺少交付授权时记录待执行动作，继续已授权工作，未创建的 PR 不记为已交付。
6. 完成当前步骤或创建 PR 后继续推进，直到请求范围内的实现、验证和交付完成。只有用户要求暂停、依赖的检查/合并/发布条件未满足或缺少必要授权时暂停受影响步骤；不依赖该结果的已授权批次可继续。全部任务完成后在计划头部写 `**状态：** 已完成 (YYYY-MM-DD)`。
7. 每次阶段汇报给出已完成任务数与总任务数、当前任务和步骤、修改文件、验证结果、阻塞点和下一步；任务总数变化时说明原因。已完成历史只引用计划中的关键证据或 commit、PR、Pre、deploy 等标识，不重复完整过程。

## 技能加载检查

- 从计划及关联任务文件、用户要求和仓库规范中提取技能要求，区分当前任务必需、条件触发和后续任务使用的技能；执行到适用步骤前加载，不提前读取所有依赖。
- 按当前环境的技能发现与读取方式，实际读取所需技能的 `SKILL.md`，并按其指引读取当前步骤必需的引用文件和依赖技能。技能出现在目录、清单、计划或 `metadata.depends_on` 中不代表已加载；当前上下文已保留完整适用指令时无需重复读取，仅凭名称或历史“已加载”记录不能跳过。
- 在任务执行记录中简要列出当前所需技能的名称、来源路径或资源标识及加载结果，并在执行前汇报中说明；上下文丢失或加载证据不足时重新读取。将适用约束落实到当前修改和验证中，不能只记录名称。
- 找不到或无法读取必需技能时，先尝试环境支持的发现方式及可能变更的路径；仍无法加载则记录缺失技能、受影响步骤和恢复条件，暂停依赖步骤，继续不依赖它的已授权任务，不得把该技能标为已加载。

## 硬约束

- 每份计划文件最多 256 KiB（262144 字节，按 UTF-8 保存后的实际字节数计算）。读取和回写计划时用 `wc -c <计划文件路径>` 检查；超限时按 `write-project-plan` 的文档结构拆分，更新主计划和任务文件间的链接，保留任务编号、状态、证据及依赖顺序。全部任务是否完成须覆盖所有关联文件。
- 计划是执行依据，不是敏感操作的授权。“执行计划”“继续”“自动完成”等概括性要求、计划已确认或检查通过，均不能代替用户对具体敏感操作的明确确认。
- 合并 PR（含启用自动合并）、生产上线或发布阶段推进、回滚或中止发布、生产数据写入或删除、破坏性操作（如强推或删除共享分支）均须先取得用户明确确认，并满足对应技能和仓库的验证要求；不得以脚本、子代理或其他间接方式绕过确认。
- 确认须覆盖具体动作、对象和范围，例如 PR 与待合并版本，或应用、环境、发布版本及阶段；已有明确确认仅在其范围内有效，不能外推到其他 PR、版本、环境、发布阶段或异常处置。确认不等于豁免失败检查或监控要求。
- 计划可以包含提交、推送和 PR；Agent 可在已授权交付范围内推进到可审查或可合并状态。未获用户明确确认不得执行敏感操作；缺少确认时只暂停相关操作及依赖步骤，继续不依赖它的已授权工作，并将待确认项留为未完成。
- `docs/agent_plans/`、`.agents/plans/` 等计划文件默认只作本地执行记录，不进 stage、commit 或 PR，除非用户明确点名。
- 不为赶进度跳过验证、弱化断言或把未验证、pending、空指标写成完成；验证结果必须与实际证据一致。
