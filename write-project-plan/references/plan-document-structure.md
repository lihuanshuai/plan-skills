# 计划文档结构

遵守 `write-project-plan` 的实现选择、计划语言和验证要求；按实际任务增减模板条目。

## 单文件大小与拆分

每份计划文件最多 256 KiB（262144 字节）。写入或更新后用 `wc -c <计划文件路径>` 检查实际字节数，不能以字符数或行数代替。

超限时，主计划保留文档头部、完整任务总览和执行顺序，将具体任务按任务或独立交付边界移至同目录的关联文件。目录和总览使用相对链接指向对应文件及任务锚点；各关联文件链接回主计划，写清所含任务、前置依赖及必需的公共约定。任务编号在整份计划中保持唯一，具体任务沿用下文格式。单个任务仍超限时，按可验证步骤继续拆分，并注明依赖顺序和任务完成条件。

拆分后逐份检查大小和链接；主计划也须满足大小上限。不得通过删减验收条件、验证证据或必要实现细节满足限制。

## 文档头部

```markdown
# [功能名称] 实施计划

**目标：** [一句话描述最终产出]

**架构：** [2–3 句说明实现路径、关键边界和依赖顺序]

**技术栈：** [真实使用的关键技术或库]

**关联：** [Issue、需求文档或其他证据链接]

**假设：** [仅列出无法直接验证但不阻塞规划的假设；没有则写“无”]

## 目录

- [任务总览](#任务总览)
- [任务 1: [项目或组件] — [阶段目标]](#task-1)

---
```

目录按实际任务增减条目，链接文字与任务标题一致；任务编号或数量变化时同步更新目录。

## 术语表

计划引入新术语、缩写或概念，或使用读者可能不熟悉的项目专用含义时，必须在目录之后、任务总览之前加入“术语表”，并在目录中添加链接。只收录理解当前计划所需的条目；没有此类内容时省略，不创建空表。

```markdown
## 术语表

| 术语或概念 | 通俗解释 | 本计划中的用途或示例 |
| --- | --- | --- |
| [准确名称或缩写，缩写注明全称] | [不依赖其他未解释术语的说明] | [对应对象、使用场景或具体例子] |
```

正文首次使用时简短解释或链接到对应条目，全文保持同一含义。拆分计划时，在关联文件中链接主计划的术语表；仅在单个任务中使用的术语可在对应文件内设置术语表，并从首次出现处链接。

## 任务总览

放在第一个具体任务之前，按独立交付边界与实际依赖关系列出任务，不固定数量；简单改动可只有一个任务，不为填充模板拆出额外任务或阶段。每条必须映射到后续任务。跨项目任务标明项目和依赖关系。

```markdown
## 任务总览

- 任务 1: [阶段目标]；产出 [关键文件、接口或行为]；验证 [主要命令或验收方式]
```

## 分批提交与 PR

包含代码或配置改动时，按 `write-project-plan` 的“分批交付”填写，放在任务总览之后，并在目录中添加链接。表中计划标识与具体任务的“所属 PR 批次”对应。

```markdown
## 分批提交与 PR

| 计划 PR | 目标仓库与任务/commit | 改动范围与预计规模 | 前置 PR/版本 | 验证与可审查条件 | 提交、合并与发布顺序 | 回滚方式 |
|---|---|---|---|---|---|---|
```

各批最后一个任务写明交付步骤、完成证据和下一批开始条件；敏感操作沿用下文的确认要求。拆分计划时，此表保留在主计划，任务文件链接回对应批次。

## 具体任务

```markdown
<a id="task-N"></a>

### 任务 N: [项目或组件] — [阶段目标]

**状态：** 未开始

**完成标志：** [可客观判定的条件]

**所属 PR 批次：** [对应“分批提交与 PR”中的唯一标识及前置条件]

**文件：**
- 创建或修改: `exact/path/to/file` — [符号或配置项及职责]
- 测试: [适用的现有或新增测试位置；不适用时说明验证方式]

**实现约定：** [接口输入输出、兼容要求、关键算法或配置行为]

- [ ] **步骤 1: [具体动作]**

[修改位置、动作与预期行为；仅在需要消除歧义时提供关键代码]

- [ ] **步骤 2: 验证任务完成**

运行：[能证明完成条件的精确命令及仓库必跑项]。

预期：[可观察结果和关键回归行为]。
```

将 `task-N` 中的 `N` 换成实际任务编号，确保每条目录链接指向对应任务且锚点不重复。

交付步骤按任务需要添加：

- 提交、推送或 PR 步骤按已授权交付范围安排；提交时列出精确文件，计划文件默认不纳入提交。
- 涉及合并 PR、生产上线或发布阶段推进、回滚或中止发布、生产数据写入或删除、破坏性操作时，将准备、验证与实际操作分开；实际操作步骤标注“执行前需用户确认”，列出具体对象、范围、验证结果、风险和回退方式。已有确认只在原范围内有效，不能从确认整个计划推导敏感操作授权。

## 状态机制

- 任务状态：`未开始` → `进行中` → `已完成 (YYYY-MM-DD)`。
- 步骤状态：验证通过后把 `- [ ]` 更新为 `- [x]`。
- 完成标志必须可客观判定，例如指定测试通过、Pre 验证通过或 PR 达到可合并状态；包含敏感操作的任务，取得用户明确确认并核实实际执行结果后才可完成。等待确认时记录待确认对象、范围和恢复条件，保留实际操作及依赖步骤未勾选。
